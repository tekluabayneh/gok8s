Comment framework for deep systems learning while building Kubernetes from scratch

For every piece of code you write, go through these 6 categories. Not every question applies every time — but the ones that do belong as a comment above the code, not in your head.
1 Memory — where does this data live?
Does this variable escape to the heap, or stay on the stack?
run: go build -gcflags="-m" to see what Go decides
If I take the address of this (&x), what happens to x's lifetime?
address taken = likely heap allocated = GC pressure
When this function returns, what memory gets cleaned up and what survives?
stack frame = instant gone. heap = waits for GC
Am I copying a value or sharing a reference? What's the cost difference?
big struct copy = slow. pointer = cheap but shared state risk
// MEMORY COMMENT EXAMPLE: // pod is a pointer — Go escape analysis will move this to the heap // because we return &pod, meaning it must outlive this function's stack frame. // Cost: one heap allocation + GC will eventually collect it. // Trade-off: we WANT this — the scheduler needs pod to survive. func newPod(name string) *Pod { pod := Pod{Name: name} return &pod }
2 Concurrency — who owns this data right now?
Can two goroutines touch this at the same time? What goes wrong if they do?
data race = undefined behavior, crashed nodes, corrupted state
Is this a channel (communication) or a mutex (protection)? Why did I choose this one?
Go proverb: "share memory by communicating" — channels often cleaner
Where does this goroutine die? Who is responsible for stopping it?
goroutine leaks are invisible — always have a cancellation path
What is the happens-before guarantee here? Can I read a stale value?
without sync, goroutine B may never see goroutine A's write
// CONCURRENCY COMMENT EXAMPLE: // mu protects nodeList — multiple goroutines (scheduler, health checker, // API handler) all read/write this. Without mu, two goroutines could // write simultaneously → slice corruption → crashed control plane. // We use RWMutex: many readers OK at same time, writer gets exclusive lock. mu.RLock() nodes := nodeList mu.RUnlock()
3 Control flow — what happens at runtime, step by step?
When this for loop runs, where do the loop variables live? Do they escape?
classic Go bug: goroutine inside loop captures loop variable by reference
What is the worst-case number of iterations here? Can this loop block forever?
infinite retry loops need backoff + timeout or they eat CPU
When this function returns an error, what state did I leave behind?
partial writes, half-created resources, open connections = ghost state
Does defer run here even on panic? What cleanup am I relying on it for?
defer runs on panic too — good for unlock, close, cleanup
// CONTROL FLOW COMMENT EXAMPLE: // DANGER: classic Go closure-in-loop bug. // Without `node := node`, every goroutine captures the SAME loop variable. // By the time goroutines run, the loop is done → all see the last node. // The copy creates a new stack variable per iteration → each goroutine // gets its own independent value. for _, node := range nodes { node := node // shadow: force new stack variable each iteration go healthCheck(node) }
4 OS & kernel — what syscall is hiding under this?
What OS syscall does this trigger? (read, write, epoll, clone, execve…)
use strace on Linux to see every syscall your program makes
Is this blocking the OS thread, or is Go's runtime handling it async?
Go wraps blocking syscalls — it parks the goroutine, not the thread
Am I crossing a process or namespace boundary here? (cgroups, namespaces, containers)
k8s pods = Linux namespaces + cgroups — every container op touches kernel
What happens to this file descriptor / socket / pipe when the process dies?
unclosed FDs = resource leak; kernel closes them on process exit but not goroutine exit
// OS COMMENT EXAMPLE: // net.Listen() → OS syscall: socket() + bind() + listen() // The kernel allocates a socket FD and adds it to the process's FD table. // When we defer ln.Close(), that triggers close() syscall → kernel frees the port. // Without defer: port stays bound even after function returns → "address in use" error. ln, err := net.Listen("tcp", ":8080") defer ln.Close()
5 Data structures — why this shape, not another?
Why a map here and not a slice? What's the lookup cost of each?
map = O(1) lookup, slice = O(n). but map has higher allocation cost
When this map grows, what happens in memory? Does it rehash?
Go maps grow by doubling buckets — all keys rehash → latency spike
Is this slice sharing the underlying array with another slice? Can a write to one corrupt the other?
slices share array until append triggers a copy — silent aliasing bug
What's the zero value of this type, and is it safe to use without initialization?
Go zero values are usable: sync.Mutex{} works, nil slice is appendable
6 Distributed systems — what breaks when the network lies?
What happens if this RPC call times out halfway through? Is the operation idempotent?
k8s uses etcd watch loops + reconciliation to handle partial failures
What is the source of truth here — memory, etcd, the node's local state?
always reconcile against etcd, not in-memory cache alone
Can two controllers act on the same object simultaneously? Who wins?
k8s uses optimistic concurrency — resourceVersion + conflict retry
If this node crashes right here, mid-execution, what state is the cluster left in?
design every operation to be safe to re-run from the beginning
